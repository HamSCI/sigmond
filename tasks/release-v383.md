## For v3.84 (found while building v3.83)

- **T6's chain-delay calibration lives only in tmpfs** (`/run/hf-timestd/timing_chain.json`), so every reboot re-acquires T6 from scratch.  AI6VN re-acquired on a sidelobe after a reboot on 2026-10-28 (−307.8 ms against the ±250 ms bound, refused correctly) and sat on T2.  A service restart, with radiod running, re-promoted T6 in 36 s.  Two log lines alternate every ~300 s and contradict each other ("T6 IS ASSERTING" / "T6 DOES NOT ASSERT").  Needs Michael's ruling: should a validated chain delay survive a reboot, and what makes a stored one trustworthy (Rob, bus 2026-10-28 22:40Z).  Rows 7 and 8 also move here.
- `smd align` builds a component but restarts it only when it was running; a station-web that crashed between the v3.82 update and align stays down until started by hand.  `smd align`'s dry run does not list the builds it will run.
- The bring-up hardware gate runs before mag-recorder's install probe, so on a reflash it still reads the image's 0x23.
- An "unassessable" venv now plans a root build on every update.  station-web's venv goes stale when only hamsci-physics changes its dependencies.
- `smd psws restore-keys`: refuse a regular file named exactly as a tree top (crashes with IndexError when the directory is absent); refuse regular files with more than one link; reset subdirectory modes; turn a chown OSError in the owner pass into a message.
- Test-strength items from the reviews, listed in the v3.83 SDD ledger.
